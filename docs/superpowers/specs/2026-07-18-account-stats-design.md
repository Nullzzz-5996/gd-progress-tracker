# Статистика аккаунта из сейв-файла GD

**Дата:** 2026-07-18
**Статус:** утверждён, готов к планированию реализации

## Задача

Вкладка «Статистика» должна показывать статистику аккаунта Geometry Dash, прочитанную из
сейв-файла на этом компьютере, **независимо от того, есть ли уровни в БД трекера**.

Сегодня страница строится исключительно по таблице `Levels`
(`src/GdTracker.ViewModels/StatsViewModel.cs:31-32` — `GetAllAsync()` → `StatisticsCalculator.Compute`).
При пустой БД она не падает, но показывает нули и пустые графики: шесть карточек по нулям,
`OfficialProgress = "0 / 0"`, круговая диаграмма из одной легенды.

## Почему это нельзя решить импортом уровней

Счётчики аккаунта — независимый источник данных, а не производная от списка уровней.
Замер на реальном сейве (1227 уровней) показал систематическое расхождение:

| Показатель | `GS_value` | Посчитано по уровням сейва |
|---|---|---|
| Официальные уровни на 100% | 27 | 27 |
| Онлайн-уровни на 100% | 322 | 294 |
| Демоны | 17 | 14 |
| Звёзды | 886 | 579 |
| Попытки | 43 329 | 39 234 |

Счётчики накопительные и не уменьшаются, когда уровень исчезает из локальных записей.
Восстановить их агрегацией таблицы `Levels` невозможно даже при полном импорте.

## Источник данных

Блок `GS_value` внутри `CCGameManager.dat` — словарь из ~120 записей: числовые ключи `1..43`
и ~77 записей вида `unique_<levelID>_<coinIdx>` (флаги собранных монет официальных уровней).

Расшифровка ключей нигде официально не документирована. Проверялась по двум независимым
линиям источников (GD Docs / boomlings.dev и линейка gd.py + GDColon) с состязательной
перепроверкой каждого утверждения. Якорь выравнивания индексов — ключ `3`, сошедшийся точно
с локально посчитанным числом официальных уровней на 100%; величины ключей `4/5/6` совпадают
с масштабом «322 онлайн-уровня / 17 демонов / 886 звёзд». Сдвиг на единицу сломал бы все три сразу.

### Показываемые метрики (9 штук)

| Ключ | Метрика | Подпись в UI |
|---|---|---|
| 6 | Звёзды | Звёзды |
| 28 | Луны | Луны |
| 5 | Демоны пройдены | Демоны |
| 4 | Онлайн-уровни пройдены | Онлайн-уровни |
| 3 | Официальные уровни пройдены | Официальные уровни |
| 8 | Секретные монеты | Секретные монеты |
| 2 | Попытки за всё время | Попытки |
| 1 | Прыжки за всё время | Прыжки |
| 22 | Сферы за всё время | Сферы (всего) |

Две подписи обязательны именно в таком виде, иначе ошибка будет незаметна при тестировании:

- ключ `8` — **секретные** монеты (84); ключ `12` — пользовательские монеты (82). Значения
  близкие, перепутать легко;
- ключ `22` — сферы **за всё время** (49 359); ключ `14` — текущий баланс (10 682).

### Что сознательно не показываем

- Ключи `16-19` и `23-27` — счётчики осколков. То, что это осколки, подтверждено; какому ключу
  какая стихия соответствует — источники называют по-разному, и данные спор не разрешают.
- Ключи `30-39` — прогресс путей. В проверенном сейве все нули, подтвердить нечем.
- Ключи `29` и `43` — три источника дают три разных названия.
- Ключи `40-42` (гонтлеты, награды списков, insane-уровни) — одна линия источников без
  независимого подтверждения.

Эти значения всё равно попадают в архив снимка (см. ниже), просто не выводятся на экран.

## Архитектура

### Стоимость чтения

Замер на реальном файле 55,8 МБ:

| Операция | Время |
|---|---|
| Чтение файла с диска | 43 мс |
| `SaveFileCodec.Decode` (XOR → base64 → gzip) | 714 мс |
| `SaveFileParser.Parse` (полный разбор уровней) | 389 мс |
| Поиск и разбор блока `GS_value` в готовом XML | 8 мс |

Пик памяти — 604 МБ на проход: декодированный XML это 56 млн символов в одной строке.
Отсюда два следствия: полный разбор уровней ради статистики не запускаем, и сейв не
перечитываем при каждом заходе на вкладку.

### Выбранный подход

Отдельный парсер поверх существующего кодека. Альтернативы отклонены:
расширение `SaveFileParser.Parse` меняет публичную сигнатуру, ломает существующие тесты и
связывает импорт уровней со статистикой — тогда как задача требует ровно независимости;
потоковое чтение снизило бы пик памяти до единиц мегабайт, но `GS_value` лежит в самом конце
файла (позиция 55 939 280 из 56 259 372), поток всё равно проходит весь файл, а кода прибавляется
заметно — и всплеск в 600 МБ у приложения уже есть сегодня при импорте уровней.
Зафиксировано как возможная последующая оптимизация.

### Компоненты

**GdTracker.Core**

- `Models/AccountStats.cs` — запись с девятью значениями (`long`) и `CapturedAt`.
  Отсутствующий в файле ключ даёт `0`, а не исключение: сейвы версий до 2.2 не содержат
  ключей `23+`, и приложение обязано это пережить.

**GdTracker.GameSync**

- `AccountStatsParser.cs` — чистый статический класс: `Parse(string xml) → AccountStats`.
  Находит `<k>GS_value</k>`, разбирает его словарь, возвращает запись.
  Номера ключей — именованные константы с комментарием об источнике и уровне доверия.
  **Обязательно:** нечисловые ключи (`unique_*`) пропускаются. Разбор всех ключей через
  `int.Parse` уронит парсер на реальном файле — там таких записей ~77.
- `SaveFileReader.cs` — метод `ReadAccountStats(path)` рядом с существующим `ReadLevels`,
  с тем же режимом доступа `FileShare.ReadWrite` (игра может держать файл открытым).

**GdTracker.Data**

- Сущность `AccountStatsSnapshot`: `Id`, `CapturedAt`, `SaveFileWrittenAt`, девять колонок
  метрик и `RawValuesJson` — сырой JSON всех числовых ключей `GS_value`.
  Архив нужен потому, что это единственное, что нельзя добавить задним числом: без него
  история по любой метрике вне девятки начнётся с момента будущей доработки, а не с сегодня.
  Записи `unique_*` в архив не попадают — это флаги монет, а не статистика.
- Миграция EF (третья в проекте).
- `IAccountStatsRepository`: `GetLatestAsync()`, `AddIfChangedAsync(stats)`.
  Новая строка пишется только если хоть одно из девяти значений отличается от последнего
  снимка. Сравнение по значениям, не по `RawValuesJson`: иначе любой посторонний ключ,
  меняющийся при каждом запуске игры, будет плодить строки.
  Метод в любом случае возвращает актуальный снимок — новый или существующий, — чтобы
  вызывающей стороне не приходилось делать повторный запрос.

**Настройки**

- `ISettingsService` поверх `settings.json` в `%LOCALAPPDATA%\GdTracker\` (рядом с БД,
  путь через существующий `AppPaths`). Хранит путь к сейв-файлу.
- Значение по умолчанию — существующий `SaveFileLocator.DefaultGameManagerPath()`.
- `LevelsViewModel` переводится на тот же сервис: сейчас путь живёт только в поле
  вью-модели (`src/GdTracker.ViewModels/LevelsViewModel.cs:40`) и теряется при перезапуске.
  Заодно закрывается заглушка `src/GdTracker.App/Views/SettingsPage.xaml:11` («в Фазе 2»).
- `IFileDialogService` получает метод выбора `.dat`-файла (сейчас обслуживает только
  экспорт/импорт JSON).

**GdTracker.ViewModels**

- `StatsViewModel` получает две секции. Сверху «Аккаунт» — девять карточек из снимка.
  Снизу «Прогресс в трекере» — существующие шесть карточек и три графика без изменений.
- `LoadAsync`: сначала последний снимок из БД (рисуется мгновенно), затем фоновое обновление
  через `Task.Run` — чтение сейва, сохранение снимка при изменениях, обновление свойств.
- Фоновое чтение пропускается, если `LastWriteTime` сейв-файла совпадает с `SaveFileWrittenAt`
  последнего снимка: страницы транзиентные, и `Loaded` срабатывает при каждом возврате на
  вкладку — без этой проверки переключение туда-обратно каждый раз стоило бы секунды и
  всплеска памяти на ровном месте. Проверка времени модификации стоит доли миллисекунды.
  Игра переписывает сейв при выходе и при сохранении, так что новые данные не пропускаются.
- `RefreshCommand` читает сейв **безусловно**, игнорируя эту проверку: это осознанное действие
  пользователя и запасной выход, если время модификации почему-то обмануло.
- `IsBusy`, подпись «данные на \<время\>».

**GdTracker.App**

- `StatsPage.xaml` — секция аккаунта над существующей разметкой, стиль карточек повторяет
  текущий (`StatsPage.xaml:21-58`).

### Поток данных

```
CCGameManager.dat
  → SaveFileReader.ReadAccountStats (FileShare.ReadWrite)
  → SaveFileCodec.Decode                     [714 мс]
  → AccountStatsParser.Parse (только GS_value) [8 мс]
  → AccountStats
  → IAccountStatsRepository.AddIfChangedAsync
  → AccountStatsSnapshot в SQLite
       ↑ читается мгновенно при открытии вкладки
```

## Обработка ошибок

Страницы вызывают `LoadAsync` из обработчика `Loaded`
(`src/GdTracker.App/Views/StatsPage.xaml.cs:6-17`) — это эквивалент `async void`, и любое
исключение оттуда не наблюдается и роняет приложение. Пока страница читала только БД, риск был
теоретическим; с обращением к файловой системе он становится реальным.

Поэтому весь `LoadAsync` заворачивается в `try/catch`, ошибка уходит в свойство состояния —
по образцу `src/GdTracker.ViewModels/LevelsViewModel.cs:209-226`. Конкретные состояния:

| Ситуация | Поведение |
|---|---|
| Путь не задан и автоопределение не нашло файл | Текст с объяснением + кнопка «Указать файл» |
| Файл указан, но отсутствует | Текст с путём + кнопка «Указать файл»; последний снимок остаётся на экране |
| Файл занят или битый, декод упал | Текст ошибки; последний снимок остаётся на экране |
| Файл прочитан, но блока `GS_value` нет | Карточки по нулям + пометка, что статистика в файле не найдена |
| Снимков в БД ещё нет и сейв недоступен | Секция аккаунта показывает пустое состояние, секция трекера работает как раньше |

Ни одно из этих состояний не мешает нижней секции: вкладка остаётся полезной, даже если
сейв недоступен, ровно как и наоборот — в этом смысл задачи.

## Тестирование

Следуем существующим соглашениям: xUnit + FluentAssertions 7.2.0, рукописные фейки без
mock-библиотек, реальный SQLite через `TestSupport.InMemorySqlite`, фикстуры парсера —
синтетический plist в виде строковой константы (не настоящие `.dat`).

- `AccountStatsParserTests`: разбор всех девяти ключей; **запись `unique_*` в фикстуре
  обязательна** — это регрессия на реальную ловушку; неизвестный ключ игнорируется;
  отсутствующий ключ даёт `0`; отсутствие блока `GS_value` не бросает исключение.
- `AccountStatsRepositoryTests`: первый снимок пишется; идентичный не дублируется;
  изменённый пишется как новая строка; `GetLatestAsync` возвращает последний по `CapturedAt`.
- `SettingsServiceTests`: сохранение и чтение пути между экземплярами; отсутствующий
  `settings.json` даёт значение по умолчанию, а не исключение.
- `StatsViewModelTests` — **главный тест под требование**: пустая таблица `Levels` +
  фейковый ридер сейва → девять карточек аккаунта заполнены, секция трекера в нулях,
  исключений нет.
- `StatsViewModelTests`: недоступный сейв + существующий снимок → показан снимок и текст ошибки.
- `StatsViewModelTests`: неизменившееся время модификации сейва → повторный `LoadAsync`
  не обращается к ридеру; `RefreshCommand` обращается всегда.

## Границы задачи

Не входит: график динамики (снимки копим, рисуем позже), метрики со спорной расшифровкой,
`CCLocalLevels.dat`, поддержка нескольких аккаунтов и установок игры, потоковое чтение сейва,
исправление расхождения `Untouched`/`InProgress`/`Completed` в
`src/GdTracker.Core/Services/StatisticsCalculator.cs:40-42` (три независимых предиката,
не обязаны в сумме давать `TotalLevels`) — замечено, но к этой задаче не относится.

## Открытый вопрос к пользователю (не блокирует реализацию)

Расшифровка девяти показываемых ключей подтверждена источниками и косвенно данными, но
окончательно проверяется за минуту в игре: профиль GD показывает звёзды, луны, демоны,
секретные монеты. Если `звёзды = 886`, `демоны = 17`, `онлайн-уровни = 322` совпадут с экраном
профиля, выравнивание всей таблицы подтверждено фактически, а не выведено.
